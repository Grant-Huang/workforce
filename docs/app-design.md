# App 功能需求设计文档

这份文档是产品/功能层面的完整需求说明，覆盖三块：已经做好的东西（盘点，别重复造轮子）、正在做的这次改动（ChatGPT 风格界面 + 语音口述转文字）、以及技术方案里哪些部分是"设计好了但还没验证过"。改之前先确认这份文档跟你的预期对齐，改完之后这份文档也应该保持更新，作为以后接手的人的入口。

## 一、整体视觉方向：参照 ChatGPT App

用户提供的参考截图（Grok / ChatGPT iOS App）核心特征：

- 极简、留白多，顶部只有最基本的图标（菜单、设置/历史），没有大标题栏
- 中间大片空白，没有对话时不堆内容
- 底部一条**胶囊形输入栏**浮在屏幕下方：文字输入框 + 麦克风图标
- 进入语音口述状态后，输入栏变成：取消（X）+ 波形动画 + 停止（■）+ 发送（↑，蓝色圆形按钮）

这个方向跟这几天在网页 demo 上做的"克制的建议按钮"设计思路是一致的（不主动说话、不主动连接、只在空状态给最多 1 条建议），这次要把这个"克制"的原则贯彻到整个界面视觉上，不只是建议按钮这一处。

**已完成**（2026-08-23）：网页 demo 和 iOS 都改成了"文字输入胶囊 + 语音对话按钮同一行并排"的布局，去掉了占地方的标题栏文字，缩小了语音按钮（从占一整行的大圆按钮，改成跟输入胶囊同高、贴在旁边的小圆按钮），空状态的文案往下挪、留白加大。网页版用 Playwright 截了图验证过（空状态/打字中/口述中/对话中四种状态布局都正常），也重跑了一遍功能回归测试确认没有破坏交互逻辑；iOS 端做了同样的结构调整，但跟这次其他 iOS 改动一样没有编译验证过。

## 二、三种交互模式

App 里实际上有三种不同的"用户怎么把话传给模型"的方式，容易混在一起说成"语音功能"，但技术实现和用户预期完全不同，需要分开设计：

### 模式 1：实时语音对话（已有）

按麦克风 → 建立 Realtime 长连接 → 用户说话 → 服务端识别到说完了 → 模型**用语音**回复 → 可以随时打断。这是现在"点麦克风"默认进入的模式，走的是 `ConversationViewModel.start()` 那一整套 Realtime 协议管线。**不变**。

### 模式 2：打字发文字（已有，iOS 刚补上）

正常打字，走文字消息。这条路径本来只有网页 demo 有，iOS 是这次刚加上的（见上一个 PR）。**不变**。

### 模式 3：语音口述转文字（新需求，之前完全没有）

用户想发一条**文字消息**，但懒得打字，想直接说出来。跟模式 1 的关键区别：

| | 模式 1：实时语音对话 | 模式 3：语音口述转文字 |
|---|---|---|
| 用户说完之后 | 模型**语音回复**，对话继续 | 语音被转成**一条文字消息**，等着发送，不产生语音回复 |
| 逐字转写还是整理过的 | 不涉及给用户看转写文本 | **必须整理过**（类似 Typeless）：去掉口语填充词、重新组织成通顺书面文字，不是逐字照抄 |
| 交互终点 | 持续对话 | 一条文字消息进了聊天记录（发送方式看用户按哪个键，见下面） |

**UI 流程**（对照 ChatGPT 截图）：

1. 点输入栏里的麦克风图标 → 进入口述录音状态，输入栏变成：**X（取消）** + 波形动画（显示正在录音）+ **■ 停止** + **↑ 发送**（蓝色圆形按钮）
2. 用户说完，有三种收尾方式：
   - 点 **X**：取消，什么都不发生，回到打字状态
   - 点 **■（停止）**：停止录音 → 语音识别 → AI 整理 → **整理后的文字回填到输入框**，用户可以看、可以改，改完自己再点发送
   - 点 **↑（发送）**：停止录音 → 语音识别 → AI 整理 → **直接作为消息发出**，不用二次确认

这两个按钮的语义由用户这次明确给出："取决于用户按哪个键，有两个，一个是直接发送，一个是修改后发送。" 对应到 UI 上就是"■ 停止"（编辑后发）和"↑ 发送"（直接发）这两个按钮，不是同一个按钮的两种状态。

## 三、模式 3 的技术方案

这是全新的一块，之前的三种模式（实时对话、打字、建议按钮）都不需要"语音转文字+AI整理"这个组合，需要单独设计。

### 3.1 语音识别（拿到用户说了什么）

**方案**：复用已经在用的 Realtime 连接机制，而不是接一个全新的语音识别 API。原因：Realtime 协议本来就会把用户说的话识别成文字，通过 `conversation.item.input_audio_transcription.completed` 事件发回来（iOS 里对应 `RealtimeClient.onUserTranscript`，网页里对应同名事件）——现在的实时语音对话模式，每一轮都在用这个事件拿到用户刚说的话，只是拿到之后紧接着做了"检索记忆 + 触发语音回复"（`groundAndRespond`）。

口述模式要做的，是**拿到同样这个转写事件，但不触发回复、不检索记忆**，转而把文本送进下一步（AI 整理）。也就是说，连接建立和音频采集这部分代码可以直接复用，只是从"转写完之后做什么"这个分支点开始走一条新路径。

### 3.2 AI 整理（Typeless 那一步）

**方案**：这一步**不建议**试图在 Realtime 连接里用某种"只要文字不要语音"的模式硬凑——Realtime 协议本来是为语音对话设计的，让它做纯文本清理任务，行为没有验证过，容易踩到未知的坑（这几天已经在 Realtime 协议的各种边界行为上吃过不少亏）。

改用**一次独立的、普通的文本 LLM 调用**（不是 WebSocket 长连接，就是一次性的 HTTP 请求），用 Qwen 的标准文本模型（比如 `qwen3.5-plus` 或者更轻量的版本，具体选型看响应速度实测），配一个专门写清理任务的 system prompt，大致方向：

> 把用户口述的这段话，整理成一段通顺、结构清晰的书面文字。去掉口语里的语气词、重复、停顿词（"呃""就是""然后""那个"这些），如果用户说话时想到哪说到哪、顺序乱，帮 TA 理顺逻辑顺序，但**不要添加原话里没有的信息，不要过度概括丢失细节**，保持第一人称语气，不要用列表/编号这种书面格式（除非原话本身就是在列举好几件事）。

这一步的输入是 3.1 拿到的原始转写文本，输出是整理后的文字，全程不涉及音频，是一次普通的文本请求，跟"记忆检索时 patch instructions"是完全独立的两回事，不要混在同一个 Realtime session 里做。

### 3.3 两个按钮怎么落地

- **停止（编辑后发）**：整理后的文字 → 写入文字输入框的 `@State`/JS 变量 → 光标聚焦、用户可编辑 → 用户手动点发送时走正常的"打字发文字"（模式 2）路径，不需要新代码。
- **发送（直接发）**：整理后的文字 → 直接调用模式 2 已有的"发送文字消息"函数（iOS 是 `ConversationViewModel.sendText(_:)`，网页是 `sendTextMessage`），跳过"回填到输入框"这一步。

两个按钮最终都汇入已经存在的"发文字消息"这条路径，新增的只是"录音 → 转写 → 整理"这一段前置流程，不需要重新实现消息发送逻辑。

### 3.4 已验证 / 仍未验证的部分（2026-08-23 更新）

**已经在网页 demo 上实现并验证**：

- ✅ **文本整理调用**（`/api/dictation-cleanup`，`qwen3.5-flash` + 上面那段清理 prompt）——用几段手写的、模拟口语的文本测过，效果符合预期（去掉语气词、理顺逻辑、不编造、不用列表格式）。
- ✅ **延迟实测，而且延迟很高、波动很大**：多次调用观察到 **17～35 秒**不等，有一次超过了当时设的 30 秒服务端超时。这不是偶发，是这个调用真实的延迟特征。已经把服务端超时放宽到 60 秒，并在前端也加了 65 秒的客户端超时兜底（`AbortController`），双重防止 UI 卡死在"整理中…"。**这个延迟量级意味着"停止说话"到"文字出现"之间，用户体感上是一段不短的等待，产品上要考虑清楚这个等待是否可接受**，比如要不要有更明确的进度提示、要不要允许用户在等待时先做别的事。
- ✅ **两个按钮的完整链路**（Playwright 端到端测试，用假麦克风设备 + 手动注入模拟转写文本，因为这个环境没有真实麦克风）：
  - "■ 停止"路径：整理后的文字正确回填到输入框，可编辑。
  - "↑ 直接发送"路径：整理后的文字正确复用已有的 `sendTextMessage`，作为一条消息发出、出现在聊天记录里。
  - 两条路径最初测试时因为等待时间不够长（等了 25-45 秒，而实际调用有时需要更久）被误判为"卡住"，加长等待后确认两条路径都能正常走完——**这个坑本身也说明了上面那条"延迟很高"结论的重要性**，测试和产品设计都得按这个真实延迟水平来，不能按理想情况估。

**仍未验证**：

- [ ] **真实语音识别**——这个环境没有真实麦克风，"用户说话 → 转写成文字"这一段用的是伪造音频设备，没法产生真实的语音触发 VAD。转写事件的机制（复用 `conversation.item.input_audio_transcription.completed`）在协议层面跟现有的实时对话模式共用同一套代码，理论上没问题，但没有用真实语音跑过。
- [ ] 口述过程中的打断/取消行为在真实设备上的表现（网页 demo 上代码逻辑是对的，X 按钮会正确释放音频资源，但同样受限于没有真实麦克风，没法端到端验证"说到一半改主意"这种真实场景）。
- [x] **iOS 版本已移植**（2026-08-23）：`VoiceChat/Dictation/DictationViewModel.swift`（独立的、跟 `ConversationViewModel` 分开的轻量状态机，避免两套逻辑纠缠）+ `DictationCleanupClient.swift`（对应网页版 `/api/dictation-cleanup`，同样的模型和 prompt）+ `ConversationView.swift` 里的三按钮录音行。跟网页版一样，**这次的移植本身没有编译验证过**（这个环境没有 Swift 工具链，只做了手工括号配对检查），网页版已经验证过的部分（清理调用效果、两个按钮的完整链路、延迟特征）在设计上是一致的，但 Swift 代码本身是否真的能跑起来，要等第一次 Xcode 编译才知道。

## 四、现有功能盘点（避免重复设计）

这些已经做好、正常工作，这次改动不用碰：

- **本地记忆检索**：关键词打分 + 时间衰减，`MemoryStore`（iOS）/`memory.js`（网页），已知局限是没有语义理解
- **AgentNexus 记忆同步**：iOS 连真实 AgentNexus（需要自己部署、按提案改过），网页 demo 连的是内存里的 mock server，不是真实系统
- **"记住…"意图检测**：`SaveIntent`，识别到明确的记住指令时走结构化写入，不是简单的消息记录
- **连接生命周期三条规则**：建立失败要提示、不主动断开、5 分钟无操作自动挂断——网页和 iOS 现在都有了（上一个 PR 刚补齐 iOS 这边）
- **建议按钮**：早上问日程、下午问工作总结，两边都有
- **音色选择**：Serena（默认）/Tina/Sunnybobi/Ethan/Raymond/Dylan，两边都有下拉/Picker
- **专属域名 + Workspace ID 配置**：两边都支持，没配置时回退到共享域名
