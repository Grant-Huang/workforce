# App 功能需求设计文档

这份文档是产品/功能层面的完整需求说明，覆盖三块：已经做好的东西（盘点，别重复造轮子）、正在做的这次改动（ChatGPT 风格界面 + 语音口述转文字）、以及技术方案里哪些部分是"设计好了但还没验证过"。改之前先确认这份文档跟你的预期对齐，改完之后这份文档也应该保持更新，作为以后接手的人的入口。

## 一、整体视觉方向：参照 ChatGPT App

用户提供的参考截图（Grok / ChatGPT iOS App）核心特征：

- 极简、留白多，顶部只有最基本的图标（菜单、设置/历史），没有大标题栏
- 中间大片空白，没有对话时不堆内容
- 底部一条**胶囊形输入栏**浮在屏幕下方：文字输入框 + 麦克风图标
- 进入语音口述状态后，输入栏变成：取消（X）+ 波形动画 + 停止（■）+ 发送（↑，蓝色圆形按钮）

这个方向跟这几天在网页 demo 上做的"克制的建议按钮"设计思路是一致的（不主动说话、不主动连接、只在空状态给最多 1 条建议），这次要把这个"克制"的原则贯彻到整个界面视觉上，不只是建议按钮这一处。

**已完成**（2026-08-23）：网页 demo 和 iOS 都改成了"文字输入胶囊 + 语音对话按钮同一行并排"的布局，去掉了占地方的标题栏文字，缩小了语音按钮（从占一整行的大圆按钮，改成跟输入胶囊同高、贴在旁边的小圆按钮），空状态的文案往下挪、留白加大。网页版用 Playwright 截了图验证过（空状态/打字中/口述中/对话中四种状态布局都正常），也重跑了一遍功能回归测试确认没有破坏交互逻辑；iOS 端做了同样的结构调整，但跟这次其他 iOS 改动一样没有编译验证过。

**补齐的遗漏**（2026-08-23 追加检查后发现的差距，已修）：上面这次"已完成"当时其实没做全——回头核对时发现 iOS 有三处没跟设计对齐，已经补上：
1. **消息气泡颜色没跟着换**：网页版重做时把气泡换成了 ChatGPT 那种深绿（`--user-bubble: #10a37f` 白字，助手气泡浅灰），但 iOS 当时只动了底部输入区，气泡颜色还停在最早的 `Color.blue.opacity(0.15)`/`Color.gray.opacity(0.15)`。已改成跟网页版同色号的深绿（`ConversationView.chatGPTGreen`），助手气泡用 `Color(.systemGray6)` 深浅色模式都能自适应。
2. **空状态没有引导文案**："iOS 端做了同样的结构调整"这句话没完全兑现——网页版空状态里"按下麦克风开始对话，或者直接在下面打字"这行文案 + 往下挪留白加大，iOS 当时完全没有对应的东西。已补上 `emptyStateView`（文案 + 建议按钮一起，`padding(.top, 100)` 往下挪）。
3. **口述入口在报错状态下会被锁死**：`ConversationViewModel.isIdle` 原来只在 `.idle` 时为真，`.error` 不算，导致实时语音对话一旦报错，输入胶囊上的口述按钮会一直禁用到用户把状态弄回 idle 为止——而语音对话自己的大麦克风按钮反而允许从 `.error` 直接重试。已经把 `isIdle` 改成 `.idle`/`.error` 都算"没有活动连接、可以口述"。这是行为 bug，不只是视觉遗漏；网页版没有这问题是因为网页版根本没有单独的 error 状态。

**评估后判定不用改的一处**：顶部栏结构（网页版音色选择器+状态文字堆在右上角一起走 `flex-end`；iOS 是"左边记忆图标、右边设置图标"两端分布，状态文字挪到下面单独一行，音色藏进设置页）——这其实是 iOS 更贴近设计要求的"顶部只有最基本的图标"这条描述（两个纯图标，没有状态文字/下拉框堆在顶栏里），维持现状。

## 二、三种交互模式

App 里实际上有三种不同的"用户怎么把话传给模型"的方式，容易混在一起说成"语音功能"，但技术实现和用户预期完全不同，需要分开设计：

### 模式 1：实时语音对话（已有）

按麦克风 → 建立 Realtime 长连接 → 用户说话 → 服务端识别到说完了 → 模型**用语音**回复 → 可以随时打断。这是现在"点麦克风"默认进入的模式，走的是 `ConversationViewModel.start()` 那一整套 Realtime 协议管线。**不变**。

### 模式 2：打字发文字（已有，iOS 刚补上）

正常打字，走文字消息。这条路径本来只有网页 demo 有，iOS 是这次刚加上的（见上一个 PR）。**不变**。

### 模式 3：语音口述转文字（新需求，之前完全没有）

用户想发一条**文字消息**，但懒得打字，想直接说出来。跟模式 1 的关键区别：

| | 模式 1：实时语音对话 | 模式 3：语音口述转文字 |
|---|---|---|
| 用户说完之后 | 模型**语音回复**，对话继续 | 语音被转成**一条文字消息**，等着发送，不产生语音回复 |
| 逐字转写还是整理过的 | 不涉及给用户看转写文本 | **必须整理过**（类似 Typeless）：去掉口语填充词、重新组织成通顺书面文字，不是逐字照抄 |
| 交互终点 | 持续对话 | 一条文字消息进了聊天记录（发送方式看用户按哪个键，见下面） |

**UI 流程**（对照 ChatGPT 截图）：

1. 点输入栏里的麦克风图标 → 进入口述录音状态，输入栏变成：**X（取消）** + 波形动画（显示正在录音）+ **■ 停止** + **↑ 发送**（蓝色圆形按钮）
2. 用户说完，有三种收尾方式：
   - 点 **X**：取消，什么都不发生，回到打字状态
   - 点 **■（停止）**：停止录音 → 语音识别 → AI 整理 → **整理后的文字回填到输入框**，用户可以看、可以改，改完自己再点发送
   - 点 **↑（发送）**：停止录音 → 语音识别 → AI 整理 → **直接作为消息发出**，不用二次确认

这两个按钮的语义由用户这次明确给出："取决于用户按哪个键，有两个，一个是直接发送，一个是修改后发送。" 对应到 UI 上就是"■ 停止"（编辑后发）和"↑ 发送"（直接发）这两个按钮，不是同一个按钮的两种状态。

## 三、模式 3 的技术方案

这是全新的一块，之前的三种模式（实时对话、打字、建议按钮）都不需要"语音转文字+AI整理"这个组合，需要单独设计。

### 3.1 语音识别（拿到用户说了什么）

**方案**：复用已经在用的 Realtime 连接机制，而不是接一个全新的语音识别 API。原因：Realtime 协议本来就会把用户说的话识别成文字，通过 `conversation.item.input_audio_transcription.completed` 事件发回来（iOS 里对应 `RealtimeClient.onUserTranscript`，网页里对应同名事件）——现在的实时语音对话模式，每一轮都在用这个事件拿到用户刚说的话，只是拿到之后紧接着做了"检索记忆 + 触发语音回复"（`groundAndRespond`）。

口述模式要做的，是**拿到同样这个转写事件，但不触发回复、不检索记忆**，转而把文本送进下一步（AI 整理）。也就是说，连接建立和音频采集这部分代码可以直接复用，只是从"转写完之后做什么"这个分支点开始走一条新路径。

### 3.2 AI 整理（Typeless 那一步）

**方案**：这一步**不建议**试图在 Realtime 连接里用某种"只要文字不要语音"的模式硬凑——Realtime 协议本来是为语音对话设计的，让它做纯文本清理任务，行为没有验证过，容易踩到未知的坑（这几天已经在 Realtime 协议的各种边界行为上吃过不少亏）。

改用**一次独立的、普通的文本 LLM 调用**（不是 WebSocket 长连接，就是一次性的 HTTP 请求），用 Qwen 的标准文本模型（比如 `qwen3.5-plus` 或者更轻量的版本，具体选型看响应速度实测），配一个专门写清理任务的 system prompt，大致方向：

> 把用户口述的这段话，整理成一段通顺、结构清晰的书面文字。去掉口语里的语气词、重复、停顿词（"呃""就是""然后""那个"这些），如果用户说话时想到哪说到哪、顺序乱，帮 TA 理顺逻辑顺序，但**不要添加原话里没有的信息，不要过度概括丢失细节**，保持第一人称语气，不要用列表/编号这种书面格式（除非原话本身就是在列举好几件事）。

这一步的输入是 3.1 拿到的原始转写文本，输出是整理后的文字，全程不涉及音频，是一次普通的文本请求，跟"记忆检索时 patch instructions"是完全独立的两回事，不要混在同一个 Realtime session 里做。

### 3.3 两个按钮怎么落地

- **停止（编辑后发）**：整理后的文字 → 写入文字输入框的 `@State`/JS 变量 → 光标聚焦、用户可编辑 → 用户手动点发送时走正常的"打字发文字"（模式 2）路径。这条路径**不**复用 `dictationWs`：用户还要编辑、不一定会发，所以直接关掉这条连接；真正点发送时走 `sendTextMessage`（新开一条连接，逻辑不变——编辑期间没有一条"已经开着、等着被用"的连接）。
- **发送（直接发）**：整理后的文字 → 发送，但**不是**直接调用模式 2 的 `sendTextMessage`/`sendText(_:)`（那个函数在没有连接时会重新 `start()`，也就是新开一条连接、走一遍完整握手）。口述录音时用来转写的那条连接（`dictationWs`）此时其实还开着、已经握手完成，直接关掉再重开是纯浪费的一次往返。所以"直接发"改成：把 `dictationWs` **过户**给对话模块（网页是 `promoteDictationConnection`，见 3.4），只对这条已经开着的连接打一个轻量的 `session.update`（只改 `instructions` 字段，跟"记忆检索命中后 patch instructions"是同一种调用），而不是整条连接重建。

两个按钮最终都汇入已经存在的"发文字消息"逻辑（组装消息、记忆检索、触发回复），新增的只是"录音 → 转写 → 整理"这段前置流程 + "直接发"路径下连接怎么移交，不需要重新实现消息发送本身。

### 3.4 已验证 / 仍未验证的部分（2026-08-23 更新）

**已经在网页 demo 上实现并验证**：

- ✅ **文本整理调用**（`/api/dictation-cleanup`，`qwen3.5-flash` + 上面那段清理 prompt）——用几段手写的、模拟口语的文本测过，效果符合预期（去掉语气词、理顺逻辑、不编造、不用列表格式）。
- ✅ **延迟实测过，最初选的模型很慢，换个轻量模型后快了一个数量级**：最初用 `qwen3.5-flash` 做清理，实测 **17～35 秒**不等，有一次超过了当时设的 30 秒服务端超时。后来换成阿里自己更轻量的 `qwen-turbo`（同一个域名、同一个接口，只换了模型名），三次实测 **0.9～4.3 秒**，清理质量没有变差——说明瓶颈是模型选型，不是这条链路本身慢。**当前默认模型已经是 `qwen-turbo`**，60 秒服务端超时 / 65 秒客户端超时（`AbortController`）还保留着作为兜底，但正常情况下"整理中…"应该只是一闪而过，不再是需要专门设计等待体验的长耗时步骤。
- ✅ **两个按钮的完整链路**（Playwright 端到端测试，用假麦克风设备 + 手动注入模拟转写文本，因为这个环境没有真实麦克风）：
  - "■ 停止"路径：整理后的文字正确回填到输入框，可编辑。
  - "↑ 直接发送"路径：整理后的文字正确复用已有的 `sendTextMessage`，作为一条消息发出、出现在聊天记录里。
  - 两条路径最初测试时因为等待时间不够长（等了 25-45 秒，而实际调用有时需要更久）被误判为"卡住"，加长等待后确认两条路径都能正常走完——**这个坑本身也说明了上面那条"延迟很高"结论的重要性**，测试和产品设计都得按这个真实延迟水平来，不能按理想情况估。
- ✅ **"直接发"路径的连接复用优化**（2026-08-23）：加临时耗时打点测过完整链路（打点测完就删掉了，不是留在代码里的东西），"直接发"从点按钮到用户消息气泡出现，大致分四段：整理调用（~1.6s）→ **新开一条 WebSocket + 完整握手（~2.1s，占比最大的一段）** → 记忆检索命中后的 `session.update` patch（~0.7s）→ 模型开始出声（~0.5s），合计接近 5 秒。原因是"直接发"复用的是模式 2 现成的 `sendTextMessage`，它在没连接时会调用 `start()`，而 `start()` 不知道也不管口述模块那条 `dictationWs` 其实刚刚才握手完成——直接关掉重开。
  改成 `promoteDictationConnection`（把 `dictationWs` 过户成对话模块的 `ws`，只 patch `instructions` 字段而不是整条重连）之后，用 Playwright 重新测（假麦克风 + 手动注入模拟转写文本，同样的方法），"点发送"到"用户气泡出现"缩短到 **2.3～2.9 秒**（三次实测），并且确认了：气泡出现后模型确实正常出声回复（不是连上了但连接其实是死的）、`dictationWs` 正确置空、"编辑后发"路径不受影响（依旧正常关闭连接、不发送、不复用）。**这一优化目前只在网页 demo 上做了，iOS 是否已经同步移植见下面的"仍未验证"。**

**仍未验证**：

- [ ] **真实语音识别**——这个环境没有真实麦克风，"用户说话 → 转写成文字"这一段用的是伪造音频设备，没法产生真实的语音触发 VAD。转写事件的机制（复用 `conversation.item.input_audio_transcription.completed`）在协议层面跟现有的实时对话模式共用同一套代码，理论上没问题，但没有用真实语音跑过。
- [ ] 口述过程中的打断/取消行为在真实设备上的表现（网页 demo 上代码逻辑是对的，X 按钮会正确释放音频资源，但同样受限于没有真实麦克风，没法端到端验证"说到一半改主意"这种真实场景）。
- [x] **iOS 版本已移植**（2026-08-23）：`VoiceChat/Dictation/DictationViewModel.swift`（独立的、跟 `ConversationViewModel` 分开的轻量状态机，避免两套逻辑纠缠）+ `DictationCleanupClient.swift`（对应网页版 `/api/dictation-cleanup`，同样的模型和 prompt）+ `ConversationView.swift` 里的三按钮录音行。跟网页版一样，**这次的移植本身没有编译验证过**（这个环境没有 Swift 工具链，只做了手工括号配对检查），网页版已经验证过的部分（清理调用效果、两个按钮的完整链路、延迟特征）在设计上是一致的，但 Swift 代码本身是否真的能跑起来，要等第一次 Xcode 编译才知道。
- [x] **"直接发"路径的连接复用优化也已移植到 iOS**（2026-08-23）：`DictationViewModel.finishForDirectSend()`（新方法，"编辑后发"仍走原来的 `finish()`，会关闭连接）在有文字要发时不再 `disconnect()`，而是把内部的 `RealtimeClient` 实例整个交给调用方，自己换一个全新的、未连接的实例备用；`ConversationViewModel` 新增 `sendText(_:reusing:)`，接手这个连接、重新挂上自己的回调（`wireCallbacks()`），只 patch `instructions` 字段（不是完整 `session.update`/重新握手），再走跟 `sendText(_:)` 一样的发送逻辑。跟网页版对应的 `promoteDictationConnection`/`sendCleanedDictationText` 是同一个思路的移植，**同样没有编译验证过**——网页版上量到的收益（点发送到用户气泡出现从 ~3.7s 降到 ~2.3-2.9s）不能直接当作 iOS 上的数字，只能说设计上是对齐的。

## 六、会话长度、插话机制与过渡语设计（2026-08-23 讨论收敛）

### 6.1 回复长度：按内容类型分档，不完全交给模型临场判断

现状：`BASE_INSTRUCTIONS`/`systemInstructions` 里已经有"根据问题本身决定长度，先说整体再问要不要展开"的通用原则，方向是对的，但没有具体分档，这次把它细化：

- **量化前提**：语音消费速度显著慢于阅读——TTS 播报约 150-180 词/分钟（中文语音大致 200-300+ 字/分钟，看音色语速），默读理解速度普遍是这个数字的 1.5-2 倍以上。文字答案 5 秒扫一眼就懂的内容，念出来可能要 20-30 秒，而且耳朵没法像眼睛一样跳读——语音答案必须主动压缩，不能是文字答案的直接朗读版。
- **三档策略**：
  - **查询类**（新闻、天气、日程、单一事实）：1-3 句，给答案不给报告，业界惯例控制在 15-20 秒语音以内，除非用户明确要求展开
  - **列举类**（多条新闻摘要、多条待办）：一口气最多说 3 条左右（对应人一次性靠听觉记住的条目数量上限，工作记忆容量 4±1 的认知研究结论），其余"要不要都说说"
  - **分析/解释类**：允许长，但按自然的"段落边界"切开（"第一……第二……"这种口语化分段），给用户创造插话的自然缝隙，不是不停顿的独白
- **一致性技巧**：长回答先给"路线图"句子（"这个问题我从两个角度说：一个是……，另一个是……"）；说了几点就是几点，不能中途冒出没预告的内容——语音场景比文字场景对这条要求更严格，因为听众没法"往回听"检查逻辑是不是乱了。
- **分类机制**：交给提示词/大模型隐式完成分类，跟"按对应策略生成回复"放在同一次生成里，**不做成"先分类一次调用、再回答一次调用"的两段式架构**——这个 App 的延迟预算不允许平白多一次网络往返。正则/规则（比如 `SaveIntent` 那样的强信号场景）不适合这里，"这条问题该长答还是短答"本质上依赖语义理解，规则会比文本场景更脆弱（语音输入是 ASR 转写出来的，用词更随意、可能有识别错误）。
- **待做**：把 `BASE_INSTRUCTIONS`/`systemInstructions` 里笼统的"长度自己判断"细化成上面三档的具体指引（网页、iOS 两处系统提示词都要改）。

### 6.2 插话机制：现状与已知缺口

两端都用 Realtime 协议的 `input_audio_buffer.speech_started` 事件触发打断，但完整度不一样：

- **iOS**：本地停播（`AudioIOManager.interruptPlayback`）**同时**发 `response.cancel`（`RealtimeClient.cancelResponse`）——完整的打断。
- **web**：目前只调了 `stopPlayback()`，没有发 `response.cancel`——服务端不知道自己被打断了，会继续生成/推流，属于已知 bug（见 `docs/roadmap-todo.md`）。
- **回声消除（AEC）是打断机制能可靠工作的前提**：不然麦克风会把助手自己的声音当成"用户在打断"，自己打断自己。iOS 靠 `AVAudioSession` 的 `.voiceChat` 模式拿到系统级 AEC；web 依赖浏览器 `getUserMedia` 的默认行为，没有显式声明 `echoCancellation: true`，没有实测过是否可靠。
- **VAD 阈值**（`threshold`/`prefix_padding_ms`/`silence_duration_ms`）已经暴露成 `session.update` 里的参数，但没有针对真人说话调过——这是打断体验灵不灵敏、会不会被呼吸声/背景噪音误伤的真正调节旋钮，等能上真机测试了应该优先调这个。

### 6.3 过渡语（filler phrases）：延迟掩盖机制的设计方向

**背景**：这个问题目前还不是这个 App 的实际痛点——现有的记忆检索是纯本地计算（`LocalMemory.search`，不走网络），发生在模型开始说话**之前**，不存在"说到一半停下来等结果"的情况。这个问题会在以后接入真正耗时的外部动作时（比如实时新闻搜索这类还没做的能力）变成真问题——这里先把设计方向定下来，留着以后接的时候直接用，不是现在就要实现。

- **核心原则**：过渡语存在的唯一目的是对抗延迟，本身不能反过来制造延迟。默认方案是**预先写好一批文本模板、运行时挑选**，不是现场调用大模型生成一句过渡语——现场生成等于在你想掩盖的延迟前面又插了一次延迟，除非能验证协议层支持"过渡语是流式回复里最先吐出来的、且完全不依赖工具调用结果先返回"，这一点目前没验证过，不能靠理论推断。
- **音色是合成参数，不是文本内容**：`voice` 只影响"这行字怎么被念出来"，不影响"该写哪行字"——过渡语文本库是纯文字、跟音色无关，**不需要为 6 个音色分别设计文案**，加新音色也不需要多做任何事。
- **实现路线**（两选一，取舍在于要不要绕开当前 Realtime 会话、用本地预渲染音频播放）：
  - **路线 A（推荐）**：只存文本模板（几个类别 × 3-5 句，总共十几到二十句），运行时在同一条已经打开、已经配好当前音色的 Realtime 连接上，把这句文本当一次正常的助手发言触发合成——不需要额外生成/存储任何音频资源，天然对所有音色通用。
  - **路线 B**：为每句模板 × 每个音色预先合成好音频文件（批量调用 TTS 生成，存成资源打进 App），本地播放，做到真正零延迟。代价是要维护"N 句 × 6 音色"份音频资源，改一句文案、加一个新音色都要重新生成一轮——考虑到过渡语要掩盖的是秒级的工具调用延迟，路线 A 里"让已经开着的连接念一句话"的延迟（远小于 1 秒）跟要掩盖的对象比可以忽略，不值得为了省这点时间背上路线 B 的资源维护成本。
  - **结论：走路线 A**，文案跟音色解耦，只写一份。
- **文案怎么产出**：不是运行时调用模型生成，是**一次性人工撰写/审校，作为静态数据提交进代码库**——跟现在 `VOICE_OPTIONS`、`BASE_INSTRUCTIONS`、`DICTATION_CLEANUP_PROMPT` 这几个常量走的是同一套模式：写一次、人工审核语气/安全性、提交进源码，不是运行时生成的东西。可以用大模型辅助起草候选文案（一次性建议几十条候选，人工挑选/改写后定稿），但定稿这一步必须人工过一遍——过渡语会被反复播放给用户听，不能有运行时生成内容那种"万一说错话"的不确定性。
- **可选的槽位增强**：模板可以留 1-2 个可替换变量（"让我看看关于 {主题} 的记录"），槽位内容从当前这轮用户说的话里做简单截取/规则填入，不额外调用模型——保留"听起来有针对性"的效果，同时这一步依然是本地零延迟操作。
- **待做**（等真正要接外部工具调用能力时再动手，现在不是阻塞项）：
  - 起草文案库（几个类别 × 3-5 句），人工审校定稿
  - 验证 Realtime 协议在"工具调用进行中"这个阶段，能不能先说一句预设文本、再等结果、再继续——这是路线 A 能不能落地的前提，目前完全没测过

## 七、黑话词典与记忆提炼（2026-08-23 讨论收敛）

### 7.1 热词/词汇表：实测结论

直接连了真实的 `wss://{workspace}.cn-beijing.maas.aliyuncs.com/api-ws/v1/realtime?model=qwen3.5-omni-flash-realtime`，在 `session.update` 里试了六种可能的字段形状：顶层 `vocabulary_id`、顶层 `hotwords` 数组、`input_audio_transcription.vocabulary_id`（同时试了 `input_audio_transcription.model` 换成 `paraformer-realtime-v2`/`fun-asr-realtime`/`gummy-realtime-v1` 这几个百炼文档里出现过的、支持热词的 ASR 系列型号）。

**结果**：所有尝试都被静默丢弃——`session.updated` 从不报错，但回显的 `session` 对象里也从来没出现过这些字段。唯一确认有效的是 `input_audio_transcription.model` 本身（默认 `qwen3-asr-flash-realtime`，可以换成别的模型名并被接受回显），但换任何模型名，旁边带的 `vocabulary_id` 都不会被保留。

**结论（带一个诚实的保留）**：没有证据显示 `qwen3.5-omni-flash-realtime` 的 `session.update` 支持热词/词汇表。保留意见是：测试用的是编造的假 `vocabulary_id`，没有先通过百炼独立的 `VocabularyService` REST 接口注册一个真实词表再测——但该接口文档明确写着是绑定 `fun-asr` 模型系列的，跟这个 App 用的对话模型不是一回事，即使去注册真实词表，大概率也用不到这个端点上。**结论：ASR 层面的热词偏置目前走不通，按 7.3 的方案在"事后"这层做纠偏。**

### 7.2 词典该放在哪：单一权威源 + 各端同步副本，不是"客户端 vs 服务端"二选一

讨论中提出的顾虑：以后客户端可能同时接多个后端服务获取记忆/信息，如果每个后端服务各自维护一份词典，会有多副本冲突的风险。这个顾虑是对的，但如果直接把词典放客户端，会遇到对称的问题——这个 App 本身就有 iOS/web 两端（以后还有 Android 计划），每个客户端平台各自独立维护一份词典，一样会撞上"多副本各自漂移"的问题，只是从"N 个后端"变成"M 个客户端"。

真正的原则是：**只能有一个权威版本，所有其他地方（不管是客户端还是后端服务）拿到的都是同步过来的只读副本，不能各自独立维护、各自能改**——这跟"记忆"那次讨论里"AgentNexus 是真相源、本地是同步缓存"是同一条纪律，只是这次的资源从"记忆"换成了"词典"。具体分两种词典处理：

- **个人/团队黑话**（这个人管什么叫什么，随时间增长、因人而异）：由用户在客户端使用时自然产生，**客户端是权威来源**——按第 7.3 节，这类黑话直接当成记忆的一种类型存储（打 `source: "local"`，通过第六节`记忆`讨论里设计的来源同步机制"过户"进 AgentNexus），以后不管接几个后端服务，都从 AgentNexus 读同一份，不是各自收集。
- **通用行业术语**（跟具体用户无关、不常变）：这类不是被动态编辑出来的，是一次性人工审校后当静态资源分发的，天然没有"多主体运行时修改导致冲突"这个风险，适合集中维护、分发到各端只读使用（分发机制见 `docs/roadmap-todo.md` 的"周边补全"一节）。

两条路径都遵守同一个纪律（只有一处能写，其他都是只读同步副本），跟"客户端还是服务端"这个位置选择无关。

### 7.3 记忆提炼：复用口述整理的机制，异步执行

现状确认：`handleUserTurn`/`groundAndRespond` 里，每轮**只把用户说的话原封不动存进去**（`LocalMemory.add(text)`/`memoryStore.add(userText)`，`text` 是 ASR 原始转写，未经任何整理），**助手的回复完全没有被存进记忆**。

方案：不新建一套基础设施，复用口述转文字已有的"一次性 HTTP 请求到 `qwen-turbo`"这套机制，只是换一个 prompt（从"整理成待发文字"换成"提炼这轮对话里值得记住的事实"）。跟口述整理的关键区别是**这一步完全不在关键延迟路径上**——口述整理必须让用户等着，这一步在这轮对话已经正常回复完之后**异步做**，哪怕 `qwen-turbo` 偶尔要几秒，用户也感觉不到。

具体设计：
- **user + assistant 一起喂给它**，不是只处理用户那半句——把"用户问了什么 + 助手给出的信息/结论"一起提炼成一条自洽的记忆，顺带补上"助手回复完全没被记住"这个缺口，也缓解"代词回指丢失"的问题。
- **"值不值得记"在同一次调用里判断**，不单独分类——prompt 里允许"如果这轮没有值得记的内容，返回空"，不做成"先判断要不要存、再决定存什么"的两次调用（跟第六节回复长度分类的思路一致）。
- **黑话词典作为这次调用的背景信息一起传入**——把 7.1/7.2 的纠偏需求和这一步的提炼需求合成同一次调用，不是两个独立机制。
- **原始转写仍然要保留一份可追溯的底稿**（跟"记忆"讨论里"本机暂存区"的滚动窗口是同一份数据，不是额外新增的存储）——提炼是加工，不是替换，万一发现提炼版本有问题，能回去对照原文核实。
