# 智枢记忆体系集成建议

**给谁看**：智枢（AgentNexus）后端团队
**谁写的**：语音 App（VoiceChat）项目，基于对 `grant-huang/agentnexus` 仓库当前代码的阅读
**目的**：语音 App 要把智枢当"记忆大脑"用——用户的记忆、日程、想法都沉淀在智枢里，语音 App 只是一个新的输入/输出入口（说话进、语音答）。这份文档提出三个具体的智枢侧改动建议，说明背景、现状、方案和大概工作量，供你们评估、调整、排期。

---

## 1. 背景：为什么会有这几个诉求

语音 App 的交互链路要求**低延迟**（用户说完话到 AI 开口，业界心理阈值大概是 1 秒左右），但智枢的记忆是纯服务端存储、按频道（channel）划分。如果每一轮语音对话都实时向智枢发请求查记忆，网络往返 + 查询耗时会让对话明显变卡。

因此语音 App 这边的方案是：**本地维护一份记忆缓存，跟智枢做低频后台同步，对话过程中只读本地**。这个方案本身不需要智枢改任何东西就能跑（细节见语音 App 仓库的 `docs/`），但过程中发现三处如果智枢肯改，会让这件事做得更好、也对智枢自己有好处：

1. 长期 App 集成缺一个合适的认证方式
2. 记忆层（ANCHOR/DECISIONS/PROGRESS）目前没有"定期整理/压缩"的机制，长期使用容易失控
3. "个人记忆"和"频道记忆"的关系还没有被设计出来（这是你们自己也在规划的方向，语音 App 只是第一个需要它的消费方，正好倒逼一下）

---

## 2. 建议一：让通用认证支持 `PersonalToken`（长期 Token）

### 现状

- `backend/app/db/models.py` 里已经有 `PersonalToken` 模型：长期有效、`pt_...` 前缀、只存哈希、专门为"外部长期连接"设计（模型的 docstring 原话是 "Used e.g. by Agent Bridge bot registration to authenticate as the user"）。
- 但实际上，`pt_...` 的校验逻辑目前只写在 `backend/app/agent_bridge_docs_routes.py` 的 `_resolve_user_by_bearer()` 里，是 Agent Bridge 专用的一段本地函数。
- 所有其他路由（包括语音 App 需要用到的 `backend/app/api/v1/memory/routes.py`）走的是 `backend/app/core/dependencies.py` 里的通用 `get_current_user()`，这个函数只会把 token 当 JWT 解（`decode_access_token`），不认识 `pt_...`。

### 影响

第三方长期集成（不只是语音 App，任何"我要写一个脚本/机器人/客户端长期访问智枢 API"的场景）目前只能：
- 用短期登录 JWT，过期后要重新走账号密码登录，不适合无人值守的后台同步；或者
- 只能走 Agent Bridge 那条特化的路径。

而 `PersonalToken` 这个东西看起来本来就是为了解决这个问题设计的，只是还没接到通用认证链路上。

### 建议方案

把 `_resolve_user_by_bearer()` 里 `pt_...` 那段校验逻辑，合并进 `get_current_user()`（以及同文件里的 `try_get_current_user()`），大致是：

```python
async def _resolve_user(token: str, db: AsyncSession) -> User | None:
    if token.startswith("pt_"):
        # 复用 agent_bridge_docs_routes._resolve_user_by_bearer 里已经写好的哈希校验逻辑
        ...
        return user_from_personal_token
    # 现有的 JWT 校验逻辑保持不变
    ...
```

这样任何走 `get_current_user` 的接口（记忆 API、消息 API 等等）都能直接认 `pt_...`，不用每个路由单独适配。

### 工作量估计

小改动，主要是把已经写好的一段逻辑从 `agent_bridge_docs_routes.py` 挪到/复用到 `dependencies.py` 的公共路径，核心代码已经存在，改动集中在一处，建议加几个测试用例覆盖"用 `pt_` token 调普通业务接口"这个新路径。

## 3. 建议二：记忆分层的定期整理（后台巩固/压缩）

### 现状

- `ANCHOR` / `DECISIONS` / `PROGRESS` 三层是结构化的、可 CRUD 的记忆（`backend/app/features/memory/manager.py`、`channel_memory.py`）。写入方式有两种：`save_entry`（追加一条）和 `save_layer`/`replace_layer_entries`（整层替换）。智枢自己的 AI 协作者通过 `collab_mcp` 的 `update_anchor`/`update_progress`/`update_decision` 工具（`backend/app/features/collab_mcp/tools_memory.py`）写入时用的是整层替换。
- `history` 是派生层，实时从消息表分页渲染（`history_pager.py`），**没有上限、不做压缩**——频道用得越久，这层就越大。
- 没有看到任何定时任务（celery beat 之类）会回过头去"整理"这几层——比如把很久以前的 `history` 提炼进 `ANCHOR`/`PROGRESS`，或者清理掉已经不重要的旧决策记录。

### 为什么值得做

1. **`history` 会无限增长**：现在靠"整层替换"的 `ANCHOR`/`PROGRESS`/`DECISIONS` 某种程度上已经隐含了"覆盖旧内容"的巩固逻辑（协作者每次重写整层），但这依赖协作者每次都会主动去做这件事，是被动的、不保证的。`history` 完全没有这层保护。
2. **对"个人记忆"这个新方向尤其重要**（见下一节）：如果个人记忆要综合多个频道的信息，源头频道的记忆质量（是不是已经被合理压缩、去重、保留了重点）直接决定个人记忆好不好用。垃圾进、垃圾出。
3. 对语音 App 这类"要把记忆读出来讲给用户听"的消费方来说，记忆层里的内容越精炼，语音回答的质量和响应速度都会更好——不需要每次消费方自己做二次摘要。

### 建议方案（供讨论，不是唯一解）

一个可能的设计方向：

- 加一个后台任务（按频道、按触发条件，比如"消息数超过 N 条"或"距离上次整理超过 X 天"），调用一次 LLM，把 `history` 里新增的部分 + 现有的 `ANCHOR`/`PROGRESS`/`DECISIONS` 一起喂给它，产出更新后的三层内容，写回去（复用现有的 `save_layer` 整层替换语义即可，不用新加存储结构）。
- 这个任务本质上和 `collab_mcp` 协作者机器人在做的事情是一类事，只是从"协作者主动决定要不要更新"变成"系统定期兜底一次"，两者不冲突，可以并存。
- 需要考虑：整理会改写用户手动录入的内容吗？建议整理时保留用户手动创建的条目（`creator_type == "user"`）不做覆盖，只整理/压缩机器人写入的部分，或者整理前后都保留一份历史版本方便回滚——这个策略你们比我更清楚怎么权衡，这里只提出"需要有这道工序"这个诉求，具体策略你们定。

### 工作量估计

比建议一大，是一个新功能（后台任务 + 一次 LLM 调用编排），需要你们评估优先级；如果暂时不做，也不阻塞语音 App 现在的集成，只是长期用下来体验会打折扣。

## 4. 建议三：个人记忆 vs 频道记忆的分工

### 背景

讨论下来，个人记忆的产品方向大概是：**"个人记忆" = 用户自己的私聊频道记忆 + 用户参与的所有频道记忆的某种聚合**。这个方向本身是合理的（更像一个真正了解你全部工作上下文的助理），但直接做"全量并集"会有两个问题，值得在设计阶段就考虑进去：

**问题一：不能是"全量堆一起"，得是"检索/排序"**
一个用户可能同时在几十个频道里，把这些频道的记忆全量拼给消费方（不管是智枢自己的功能，还是语音 App 这种外部消费方），信噪比会很差，也会让存储和计算成本随频道数线性增长（甚至更快）。所以"个人记忆"这个接口，从一开始就应该设计成**"给一个查询/场景，返回跨频道里最相关的几条"**，而不是"吐出全部"。

**问题二：权限要跟着当前频道成员关系走，不能是静态快照**
如果用户后来退出了某个频道，"个人记忆"聚合结果里就不应该再包含那个频道的内容。如果实现成预先摊平、定期批量算好的"个人记忆快照"存起来，容易出现"人已经不在频道里了，但个人记忆里还留着痕迹"的权限问题。建议聚合查询时**按当前成员关系现算**，或者至少在成员关系变化时有失效/重算机制，不要做成一份长期不失效的静态汇总。

### 是否需要从频道记忆里"抽取"通用内容到个人记忆？

值得做，但建议区分两种机制，而不是选其中一种：

1. **主动萃取（推荐优先做这个）**：当频道里的某条记忆明显是"关于某个具体用户"的（比如决策记录里 @了某人、指派了某人负责、todo 认领人是某人），触发时把这条记忆"提升"一份到该用户的个人记忆里，并且**带上来源频道的引用**（`source_channel_id` / `source_entry_id`），这样：
   - 用户离开来源频道时，可以级联把这条提升出来的个人记忆也失效/隐藏掉（呼应上面的权限问题）；
   - 用户能追溯"这条记忆是从哪个频道来的"，而不是一条脱离上下文的孤立信息。
   - 触发方式可以是协作者机器人在写 `ANCHOR`/`DECISIONS`/`PROGRESS` 时顺带判断，也可以是建议二里那个"定期整理"任务顺带做这件事——两个建议可以合起来实现，减少重复工作量。

2. **按需检索（作为兜底，覆盖没被主动萃取到的内容）**：额外提供一个"跨频道检索"接口，输入一个查询/场景描述，返回该用户当前有权限访问的所有频道里最相关的记忆片段，供"个人记忆"里没有覆盖到的长尾场景兜底使用。

两者的关系是：主动萃取解决"确定性强、值得长期沉淀"的内容（不用每次都现查，个人记忆库里直接就有），按需检索解决"不确定要不要沉淀，但用户问到了就得答得出来"的长尾场景。

### 工作量估计

这是三个建议里最大的一个，本质上是个新产品方向的设计+实现，建议你们内部先对齐产品设计，这份文档提供的是"外部消费方（语音 App）视角看到的具体诉求和两个要避免的坑"，不代表完整方案。

---

## 5. 对语音 App 这边的影响

以上三个建议**都不是语音 App 现在能不能跑起来的阻塞项**：

- 建议一没做之前，语音 App 先用短期 JWT + 定期要求用户重新登录/粘贴 token 顶着；做了之后只需要用户换一次 token，App 代码完全不用改（客户端视角，JWT 和 `pt_` token 都只是"往 `Authorization: Bearer` 里塞一个字符串"，没有本质区别）。
- 建议二、三都做之前，语音 App 就先只读用户的个人频道记忆，不依赖跨频道聚合。等你们有了对应接口，语音 App 那边只需要把"拉取记忆"这一步指向新接口，本地缓存的结构和同步节奏不用重新设计。
