# 语音 App 同步对话历史到智枢 —— 接口需求文档

**给谁看**：智枢（AgentNexus）后端团队
**谁写的**：语音 App（VoiceChat）项目
**目的**：语音 App 现在会把用户的语音对话实时同步进智枢里用户已有的私聊频道，让文字助理（epicwise）和语音入口共享同一份记忆。这份文档列出为了让这条同步链路跑得稳、跑得对，需要智枢侧提供或确认的具体接口点，供评估、排期。

本文档是 `docs/agentnexus-memory-integration-proposal.md`（智枢记忆体系集成建议）的姊妹文档：那份讲的是记忆体系本身的三个改进方向（认证、分层整理、个人记忆），这份聚焦在"往频道里写会话记录"这一条链路的具体接口需求，认证部分直接复用那份文档的建议一，不重复展开。

---

## 1. 背景：频道策略确认

语音 App 不会为每个用户新建一个独立频道，而是**复用用户已有的、跟 epicwise 私人助理的 1:1 私聊频道**，把语音对话作为这个频道的消息写进去。

这个选择是刻意的：语音入口和文字入口不是两个管不同领域的系统，是同一份记忆的两个输入端——用户语音里说的事，文字对话该知道；反过来也一样。如果分开建频道，在智枢还没有跨频道个人记忆聚合能力之前，会造成两个互相不知道对方存在的记忆孤岛。

这一点写在这里是想请智枢团队确认：**你们这边不需要为"语音助理"这个新入口设计任何新的频道类型或频道创建流程**，语音 App 用的就是用户现有的个人频道。真正需要智枢侧新增的，是下面几条围绕"同一个频道，多一个写入来源"产生的具体需求。

---

## 2. 建议一：消息接口能标记"仅记录，不触发 AI 协作者自动响应"（关键阻塞项）

### 现状

语音 App 把用户说的话、AI 语音助手答的话，都作为普通消息用 `POST /api/v1/channels/{channel_id}/messages` 写进用户跟 epicwise 的私聊频道。

### 问题

epicwise 作为一个会主动响应的 AI 角色，如果这条消息接口的语义是"用户发了一句话，触发 AI 协作者的对话/自动回复链路"，那么语音 App 每推一条用户的转录文本进去，可能会连带触发 epicwise **也**生成一条文字回复。而语音 App 自己已经用实时语音链路给用户答过了——结果就是同一句话被回答了两次，一次语音、一次莫名出现在聊天记录里的文字，用户体验会很诡异。

### 请求

请确认现在的 `POST .../messages` 是否会触发 AI 协作者自动响应；如果会，需要一种方式让语音 App 写入时明确声明"这是纯记录，不要触发对话链路"，比如：

```json
POST /api/v1/channels/{channel_id}/messages
{
  "content": "...",
  "sender_type": "user",
  "suppress_ai_response": true
}
```

具体是加一个 body 字段，还是拆一个专门的"仅写入"端点，由你们根据内部实现方便的方式定，语音 App 这边只需要一个明确的、稳定的方式达到"写入历史但不触发对话"的效果。

### 工作量估计

不确定，取决于现在消息写入和 AI 响应触发是否耦合在同一段逻辑里。如果本来就是分离的（比如触发响应是另一个独立的事件订阅），可能只是加一个透传的开关字段；如果耦合较深，可能需要拆分。这条建议列为**阻塞项**，语音 App 现在的推送逻辑暂时先不主动推普通对话消息，只等这个问题有明确答案后再打开。

---

## 3. 建议二：消息接口加"来源"标记字段

### 现状

`POST .../messages` 目前的 body 只有 `content`、`sender_type`，没有区分"这条消息是从哪个客户端/入口写进来的"。

### 请求

加一个可选字段，比如 `source`（或 `client_type`），语音 App 会传 `"voice-app"`：

```json
{
  "content": "...",
  "sender_type": "user",
  "source": "voice-app"
}
```

### 为什么需要

- `agentnexus-memory-integration-proposal.md` 建议二提到的"定期整理/巩固"任务，未来可以对语音来源的内容做区别对待——语音转文字有 ASR 误听的风险，巩固成 ANCHOR/DECISIONS 这类结构化记忆时可能需要更谨慎（比如置信度更低、需要人工确认之后再采纳），这个判断的前提是巩固任务能看到"这条是不是语音来的"。
- 排查问题、做可观测性时，能追溯一条记忆最初是从哪个入口写进来的。

### 工作量估计

小改动，加一个可选字段透传、原样存储即可，不需要立刻消费它（巩固任务怎么用这个字段是建议二那份文档里的事，不在这份文档范围内）。

---

## 4. 建议三：消息写入支持幂等去重

### 现状

语音 App 的推送是网络请求，会遇到超时/失败的情况。为了做"失败重试"，语音 App 需要能安全地对同一条消息重试写入，而不会造成重复消息。

### 请求

支持客户端传一个幂等键，同一个键重复提交时返回已存在的那条消息而不是新建一条：

```json
{
  "content": "...",
  "sender_type": "user",
  "client_message_id": "<client-generated uuid>"
}
```

或者用标准的 `Idempotency-Key` header，哪种方式更贴合智枢现有的接口风格由你们定。

### 工作量估计

中等，取决于现在的写入路径是否方便加一个"先查是否已存在同键记录"的判断；如果消息表已经有唯一索引类的基础设施可以复用会更简单。

---

## 5. 建议四：写入响应需要带回服务端分配的消息 ID（确认现状，非新增）

`POST .../messages` 的响应目前应该已经包含服务端分配的 `msg_id`（参考 `backend/app/api/v1/memory/routes.py` 一类的现有响应结构）。这一点在这里重申是因为语音 App 本地缓存依赖这个 ID：本机产生、还未同步的记录标记为 `source: "local"`，推送成功拿到服务端 ID 后"过户"为 `source: "agentnexus", sourceId: <服务端ID>`。只要现有响应已经带了这个字段，这条不需要额外开发，列在这里是为了显式确认，避免语音 App 这边的假设和实际接口对不上。

---

## 6. 建议五：提供"我的默认频道"查询接口

### 现状

语音 App 现在要求用户手动去智枢找到自己跟 epicwise 私聊的 `channel_id`，手动填进 App 设置里，容易配错，体验也不好。

### 请求

提供一个根据当前 token 直接返回该用户默认个人频道的接口，比如：

```
GET /api/v1/me/default-channel

Response:
{
  "channel_id": "...",
  "channel_name": "..."
}
```

这样语音 App 只需要用户填一次 token，频道就能自动关联，不需要用户自己去找、去复制 channel_id。

### 工作量估计

小，本质是"根据 user_id 查这个用户跟 epicwise 的私聊频道"，如果这个关系已经在数据模型里能查到（大概率能，既然私聊频道本来就是按用户建的），只是包一层接口。

---

## 7. 认证：复用已有建议，不重复展开

写入/读取这些接口都需要长期有效的认证方式，避免语音 App 这种无人值守的后台同步因为短期 JWT 过期而中断。这一点已经在 `docs/agentnexus-memory-integration-proposal.md` 建议一里提出（让通用认证支持 `PersonalToken`/`pt_...`），本文档直接复用那个方案，不重复展开。

---

## 8. 接入模型说明：客户端直连，不需要智枢侧的多租户/应用注册基础设施

这一点是想提前跟你们对齐范围，避免评估工作量时把不需要的东西算进去：

语音 App **不会**做成一个中心化的后端服务替所有用户去连智枢。架构是每个用户的客户端（iOS App / web）各自持有自己的 `pt_` token，直接用自己的 token 访问智枢的 REST API，权限边界完全由 token 自身的权限范围决定。也就是说：

- 智枢**不需要**为语音 App 设计任何"第三方应用注册"、OAuth 授权跳转、多用户代理管理之类的机制。
- 每个用户获取 token 的方式是自助的：用户自己在智枢生成 `pt_` token，手动贴进语音 App 的设置里——这是现在已经在用的流程，不需要新增。
- 如果以后用户规模变大，"手动复制 token"这个体验成为明显痛点，届时可以再讨论要不要做 OAuth 式的应用授权流程，但那是一个独立的、更大的话题，现阶段不在需求范围内。

---

## 9. 优先级小结

| 建议 | 性质 | 优先级 |
|---|---|---|
| 二．抑制 AI 自动响应 | 阻塞项——不确认清楚，语音 App 暂缓推送普通对话消息 | 高 |
| 一．认证支持 `pt_` token | 复用已有文档的建议，非本文档新增 | 高（另一份文档里已经在排期） |
| 三．来源标记字段 | 小改动，不阻塞，但越早有越能减少后续返工 | 中 |
| 四．幂等去重 | 中等改动，语音 App 的重试逻辑依赖它 | 中 |
| 五．默认频道查询接口 | 小改动，体验优化，不阻塞现有手动配置流程 | 低 |
| 六．消息 ID 回传 | 确认现状，预计不需要额外开发 | 低（确认即可） |
